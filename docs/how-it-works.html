Internal briefing · FDE Audit

How FDE Audit works, from screenshot to insight

A plain-language walkthrough of what this system records while you work, what it deliberately does not record, how raw screenshots become findings, and what the company learns from it.

The idea in one paragraph

While a person chooses to record a work session, a small program takes a screenshot of their active monitor every 5 seconds and notes which app and window is in front. Nothing is analyzed at that moment, and no AI is involved — it's just a camera and a notebook. Later, on demand, an AI pass reads a small sample of those screenshots, labels what kind of work was happening, and looks for patterns: repeated manual chores, two apps being juggled where one integration would do, overlapping tools across departments. The output is a set of concrete, priced improvement opportunities — automate this, consolidate that, build a small tool here.

Stage 3 · Analysis

Sessions: how a day of frames becomes chapters

Analysis doesn't look at 5-second frames one by one. It first groups them into sessions — contiguous stretches of the same working context. Each session becomes one labeled entry ("10:15–10:52, QuickBooks, bank reconciliation") rather than 440 raw frames.

A "session" here is a unit of work, not a stretch of time in the chair. It is not login-to-logout, and it is not the whole span you had the recorder running (that opt-in span is a recording session). It's a single contiguous piece of one working context — roughly one task, in one app, on one screen — that the analysis carves out on its own and labels with a capability, a description, friction, and a measured time cost. Someone who never leaves their desk still produces many sessions as they move from task to task: the unbroken morning below sits in one app the entire time and is still four separate sessions.

A new session starts when any of five triggers fires:

  • App change — switched from Excel to Chrome.
  • Window/title change — new browser page, different file open.
  • Big visual change — the screen materially changed inside the same app. This is the key one for programs like QuickBooks whose window title never changes: an invoice screen and a reconciliation screen have the same title but look completely different, so the pixel signal splits them apart.
  • Idle gap — the person stepped away and came back (short blips don't split).
  • Time cap (~10 min) — even an unbroken stretch is chunked so no single label has to cover hours.

Free pattern mining happens before any AI

Before a single screenshot is read, plain arithmetic over the metadata finds the interesting spots — this costs nothing and can run any time:

  • Ping-pong loops. Rapid alternation between two apps almost always means someone is manually carrying data between systems — the single strongest signal that an integration or small custom tool would pay for itself.
  • Recurring sequences. The same app chain every morning (Outlook → Excel → Portal) is a ritual — a report or process that's a prime automation candidate.
  • Input density. What fraction of each session had recent keyboard/mouse input. Heavy typing in an app suggests data entry (automatable); mostly reading suggests review work (a different kind of opportunity).

Stage 4 · Insights

What the company actually gains

Single observations are anecdotes. A pattern only becomes a finding after it repeats 3–4 times, and every confirmed finding is typed and priced:

Opportunity typeWhat it looks like in the dataExample outcome
AutomateSame manual sequence recurring daily/weeklyScript the Monday report — saves 90 min/week
IntegratePing-pong between two systemsConnect Excel → QuickBooks import — kills re-keying
ConsolidateSame capability spread across multiple paid apps3 departments use 3 task trackers — cut 2 licenses
Build customA chore no off-the-shelf tool covers, seen org-wideSmall internal app replaces a spreadsheet ritual
TrainFriction/slow paths where a faster feature existsTeach the shortcut; adopt the built-in report
EliminateRecurring low-value work with no downstream consumerStop producing the report nobody opens

Each finding carries an estimated minutes-per-week cost measured from real timestamps — not guesses — so "minutes × people × hourly cost" turns directly into a defensible dollar figure per opportunity, sliceable by person or department.

The end products: per-person work summaries, a ledger of confirmed improvement opportunities with time-cost estimates, per-app usage totals for license decisions, and periodic digest reports — all text, all derived, all shareable without a single screenshot leaving anyone's machine.

Privacy model, summarized

  • Opt-in recording. Capture only runs during sessions the person starts, and a pause file suspends it instantly without stopping anything.
  • Raw stays local. Screenshots and frame-by-frame records live only on the person's machine, forever. Old screenshots are auto-deleted after a retention window (default 14 days); the time-accounting notes are kept.
  • Denylist. Password managers, banking, and any configured app/site record a "was open" note but never an image.
  • What can be shared upward is only the derived text: session summaries, confirmed findings, app-usage totals, digest reports.
  • No keystrokes, no clipboard, ever. This was considered and rejected by design — the visual + timing signals get the insight without crossing into surveillance.

Rolling it out to every PC — and the analysis that pays it all back

How the recorder and the nightly analysis get onto each employee's machine, what flows to the central database, and how — once enough data has accumulated — one organization-wide pass turns thousands of individual observations into a ranked, priced improvement plan.

Two things get deployed, not one

Each employee's PC runs two separate pieces, and keeping them separate is what makes the rollout cheap and the privacy story simple:

  • The capture app — the lightweight, model-free recorder described on the first tab. It writes screenshots and metadata to the person's own disk and local database. No AI, no network traffic, never phones home.
  • The nightly analysis pass — a job that samples the day's frames, reads them with vision, and ships only the derived text — session summaries, observations, per-app usage rollups — to one central PostgreSQL database that all machines can reach over the corporate network or VPN. It can be delivered in two distinct ways (a Claude Code command, or a single self-contained API-key script) — see the two deployment methods below.
The one rule that never bends: raw screenshots never leave the machine that took them. Only text derived from them crosses the wire. A misbehaving analysis also can't corrupt the shared database — Claude emits validated structured output, and a small deterministic tool (fde_audit ingest) is the only thing holding a key to the database.

Tagging each employee to their department — automatically

Every finding in the final analysis is sliceable by department: "Finance loses 40 hrs/week to a manual close," "Procurement and Finance both pay for overlapping task-trackers." That only works if every row in the database knows which department its employee belongs to. But when IT silently pushes the agent to a few hundred Finance machines, nobody is sitting at each one to type in "Finance." So the agent labels itself, on first run, with zero per-machine setup.

Two things get resolved automatically the moment capture starts on a machine — the employee's identity and their department:

WhatWhere it comes fromWhy

Department (the label for analysis)Resolved in a two-step order — see below.AD is authoritative when it's populated; the packaged config is the guaranteed fallback.

How the department is decided — AD first, package config second

  1. Active Directory attribute (preferred). On a domain-joined machine, the agent asks the domain controller, live: "for this user's SID, what's the department attribute?" — using the built-in ADSI searcher (no extra software, no admin rights). If HR/IT keep the department field populated in AD, the machine self-classifies with the real, current department — and even self-corrects later if the employee transfers.
  2. Packaged config default (fallback). If the box is off-domain, or AD has no department set for that user, the agent silently falls back to the default_department value baked into the config.toml that shipped inside the package.
What you hand IT is opaque — they edit nothing. To roll out to Finance, you set default_department = "Finance" in the config once, on your machine, bundle it into the package, and tell IT: "push fde-audit-finance to every Finance machine." For Procurement, you cut a fde-audit-procurement package the same way. The department label travels inside the package; IT never opens a text editor, and there is no person add to run per employee. On machines where AD is populated, the agent even overrides your default with the real AD department — so the config value is just the safety net.

The net effect: one push per department, no hand-touching machines, and every session, observation, and app-usage row lands in the database already tagged with the right department — ready for the org-wide analysis to slice by team.

Two distinct ways to deploy the nightly analysis

The nightly pass can be delivered to each machine in two different ways. Both run the same analysis and write to the same central database — the difference is what has to exist on each employee's PC for the run to happen, and that difference is what decides how hard the rollout is.

Method 1 · API-key script ⭐ recommended

  • One self-contained Python script. It samples the day's frames, calls the Claude API directly with an org API key, validates the structured labels, and writes to PostgreSQL. Ship the one file and it deploys — that's the whole rollout.
  • No Claude Code needed, nothing for the employee to do. No install beyond the script, no login, no subscription — Task Scheduler runs it silently overnight.
  • Trivial to push at scale. IT pushes one file plus a service key via Group Policy / Intune to hundreds of machines; there is no per-machine auth that can silently break.
  • Billed centrally and metered. One org API key, predictable per-token cost, all spend visible in one console.

Method 2 · Claude Code

  • The analysis runs as a Claude Code command (/analyze-session) — run by hand at end of day, or headless via Task Scheduler (claude -p "/analyze-session").
  • Orchestration comes for free: retries, tool-calling, and structured-output validation are handled by the harness rather than your own code, and the versioned command file is one source of truth for everyone.
  • Runs on each person's existing Claude subscription — a small pilot costs effectively $0 extra.
  • The catch: every machine needs Claude Code installed and logged in, and that unattended auth has to keep working on every PC, forever. Fine for five volunteers; painful for five hundred machines.
Rule of thumb: Claude Code for the pilot — volunteers already have it and the marginal cost is $0 — then the API-key script for any real rollout. One Python file plus a key is a far lighter thing to push to a fleet than a logged-in Claude Code install on every PC.

Scheduling the nightly run — automated vs. manual (beta status)

Both pieces are meant to run headless via Windows Task Scheduler, and a Python script can register those tasks itself — no one has to open Task Scheduler by hand on each machine. It shells out to the built-in schtasks command, so the "install the schedule" step is just part of the push.

What it costs

  • Pilot on subscriptions (Claude Code method): the nightly run draws on each volunteer's own Claude plan — marginal cost effectively $0. Each machine's Claude Code must be logged in once so unattended runs can authenticate.
  • Rollout on an org API key (script method): metered per token, billed centrally, predictable. The pipeline reads only 1–3 representative screenshots per session — roughly 250 images per person per week — so on Claude Haiku 4.5 this comes to about $0.85 per person per week, or roughly $0.43 with the Batch API (50% off, and a nightly job is a perfect fit for async batch). The vision reads are the cost driver; the end-of-day synthesis is a handful of cheap text calls. Measure the pilot's real spend before budgeting further — see the third tab for even cheaper options.

The ultimate analysis: when the database is finally full enough

Everything above produces a steady drip into the central database: labeled sessions, per-app time totals, and observations, each tagged with a person and department. Individually these are anecdotes. The organization-wide analysis is a separate, deliberate pass that runs only once the data clears a sufficiency bar — because a pattern seen once is noise, and a recommendation built on noise costs credibility you don't get back.

When is there "enough" data?

  • Per finding: a pattern must repeat 3–4 times before it's promoted from anecdote to confirmed observation — this threshold is already built into the nightly pass.
  • Per person: a few weeks of recorded sessions, so weekly rituals (the Monday report, the month-end close) have had a chance to recur.
  • Per organization: multiple people in multiple departments contributing, so app-overlap and shared-chore patterns can be seen across teams — the questions no single person's data can answer.

What only the org-wide pass can see

The nightly per-person analysis finds individual inefficiencies. The ultimate analysis answers the questions that require everyone's data at once:

  • App consolidation. Because every session is labeled against the same fixed capability vocabulary, "which apps serve the same function?" becomes a simple query — three departments spend 40 hrs/week on task-tracking across three different paid tools is a license cut you can only see from above.
  • Shared chores. The same manual ritual appearing on ten machines is not ten small annoyances — it's one internal tool that pays for itself in a month.
  • Department-level friction. If everyone in accounting ping-pongs between the same two systems, that's an integration priority, not a training issue.
  • Onboarding maps. Aggregate work summaries show what a role actually spends time on — a ready-made map for training the next hire.

Every opportunity in the final plan carries an estimated minutes-per-week cost measured from real timestamps, multiplied out by people affected and hourly cost. The output is not "we should automate more" — it's a ranked list of specific changes, each with a defensible dollar figure, sliceable by person and department, ready to hand to whoever owns the budget. From there it repeats: implement the top items, keep recording, and let the next quarterly pass measure whether the minutes actually came back.

The payoff loop: capture is free to run, the nightly pass costs cents, and the ultimate analysis is a handful of text calls over already-aggregated data. One confirmed finding — one killed report, one integration, two cut licenses — typically repays the entire pipeline's cost for the year.

Getting the same analysis for less — the model-cost menu

The nightly vision read is the one part of this pipeline that costs real money. This page surveys cheaper ways to do that exact job — read a screenshot, emit a taxonomy label + task description + friction flags — at the same accuracy. Nothing here changes how the system works today; it is a menu of options to grow into.

First, what does it actually cost today?

Surprisingly little. The pipeline samples only 1–3 representative screenshots per session — roughly 250 images/person/week — because the dedupe and sessioning compress the day before any model sees it. At ~1,850 tokens/image on Claude Haiku 4.5 ($1/M input, $5/M output), that is about $0.85/person/week, or ~$0.43 with the Batch API (50% off, and a nightly job is a perfect fit for async batch).

So before optimizing, measure the real spend of a nightly run. The options below still help — especially multiplied across a fleet — but the starting base is already low.

These prices are for the vision model doing the image reading — a separate model call that is independent of whether the orchestration runs as a scheduled claude -p CLI job or an Agent SDK service. Whatever model does the vision read — Claude via API key included — that part need not involve Claude Code or the SDK at all; it can be a plain script, leaving Claude Code (if used) only the cheap end-of-day text synthesis.

The bigger choice hiding here: Claude Code as the engine, or a self-contained script

This is the same fork described in the deployment tab's two deployment methods, seen from the model side. Claude Code earns its keep by doing the orchestration: sampling the day's frames, calling the model, retrying failures, validating the structured label, and handing clean rows to fde_audit ingest. But that orchestration can also live in an ordinary Python script on a schedule — calling the Claude API directly with an org key, or any other model below. The script shape is what makes the rollout light; the model behind it is a separate, swappable decision.

Claude Code as the engine

  • Orchestration is free. Frame sampling, retries/backoff, tool-calling, structured-output validation, and the DB write are all handled inside the /analyze-session command — you write almost none of it.
  • One versioned command is the single source of truth; update once, push to everyone.
  • The cost: every machine needs Claude Code installed, logged in, and carrying a subscription or org API key — and that unattended auth has to keep working on each PC, forever.
  • The nightly run is Claude — you're renting the harness along with the model.

A self-contained script (any API model — Claude included — or a local model)

  • Dead-simple rollout. One Python file — grab N frames, call the vision API, write to PostgreSQL — plus a service-account key. Ship it once to every PC; Task Scheduler / cron runs it nightly with no Claude Code, no per-user login, no Claude subscription.
  • Self-contained and durable. It doesn't depend on Anthropic auth surviving on each machine or on Claude Code being present at all; the employee never has to run or log into anything.
  • The cost: you now build and maintain everything Claude Code was doing for free — frame sampling, retry logic, JSON-schema validation, error handling, and logging.
  • More upfront engineering, in exchange for a far lighter thing to push to hundreds of machines.
It isn't all-or-nothing. The common middle ground: a plain script for the high-volume vision reads — the mechanical part that needs no reasoning — while Claude is kept only for the cheap end-of-day synthesis, where its orchestration and judgment actually earn their price. That way you get the clean, subscription-free rollout for the part that runs thousands of times, and pay for the harness only where it adds value.

Option B — Run a model locally on each PC

A free, open vision model running on each employee's own machine. Zero marginal cost, and the strongest possible privacy story — screenshots never leave the device at all, not even to a model provider. A nightly batch of ~50 images tolerates slow CPU inference easily (even 60s/image is ~50 min overnight). Modern small (3–8B) open VLMs are strong at exactly this task shape: closed-taxonomy classification + short description of OCR-heavy screenshots.

Runtime & deployment

Ollama is the pragmatic Windows choice — silent per-user install (no admin), localhost OpenAI-compatible API, binds to localhost only. Push via Intune/SCCM; pre-stage the model (~4 GB for 4B, ~7–8 GB for 8B) from an internal file share rather than 500 machines pulling from the internet. Disable Ollama's auto-updater and version-pin centrally. Add AV/EDR exclusions for the multi-GB model files.

Accuracy & quality control

Constrain decoding (Ollama structured outputs / llama.cpp GBNF grammar) to force output to be exactly one of your ~20 taxonomy labels — eliminates format errors. Expect a small accuracy drop vs Claude, concentrated in confusable adjacent categories and subtle friction cues. You have free validation data: run the local model on frames Claude already labeled and measure agreement before trusting it.

The orthogonal lever — skip vision for most frames

Independent of which model above you pick, you can cut the number of vision reads dramatically. Most of a screenshot's signal is its text, obtainable for free without any vision model:

  • At capture: walk the Windows UI Automation (accessibility) tree of the foreground window — control text, dialog detection, full browser URL. Covers ~70–85% of frames in typical office apps. This is how UiPath, screen readers, and Screenpipe (the open-source Rewind alternative — the same architecture as this system) get screen text.
  • Fallback: Windows' built-in OCR (Windows.Media.Ocr, what PowerToys uses) on frames where the accessibility tree is sparse — ~99% on clean rendered screen text, ~200 ms/frame, zero install.
  • Classify from text: feed window title + app + URL + extracted text to a cheap text model (Haiku text, Gemini Flash-Lite, or a local Qwen3-4B for $0). A screen's text is ~200–600 tokens vs ~1,850 image tokens — and more information-dense.
  • Escalate only 5–10% of frames to a real vision read: low-confidence labels, low-text-but-changing screens (dashboards, design tools), suspected stuck states. This cheap-first cascade is a documented production pattern (FrugalGPT: up to 98% cost cut at matched accuracy).

What degrades without vision: capability labels and the repetitive-work flag hold up (repetition detects better from recurring titles/text than from single images); task descriptions stay near parity; the real loss is non-textual friction — spinners, frozen screens — which is exactly what the 5–10% escalation is there to catch. Error dialogs are mostly text and survive.

The end state that costs almost nothing: text-first classification (free) with a local vision model as the 5–10% escalation tier (free), reserving paid cloud calls — Claude or otherwise — for the org-wide synthesis pass, where real reasoning over aggregated data actually earns its price.
